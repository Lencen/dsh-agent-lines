# 任务委派策略：由角色线自己做，还是由线内的智能体团队做

[English](DELEGATION-POLICY.en.md) | 中文

> 版本 **v1**（2026-11-10）｜状态：生效｜维护：dsh-plugin-line
> 适用范围：三级组织下，**二级角色线**收到任务后的第一个决策。
> 更新方式见 §6（本文是活文档，随版本发布更新）。

## 0. 先说清楚"谁在判断"

- **判断由角色线会话内的负责人 agent 执行**：它按本策略 + 自己的角色卡决定"自己做"还是"开内部团队"。
- **插件侧不自动识别、不自动派发、不硬拦截**：插件提供 `subteamPolicy` / `maxMembers` 字段、只读部门视图与审计（不变量 I5）。
- 想做"硬门禁"必须先有官方的 per-line 上限或 spawn 前拦截 API；当前官方没有（见 0.6.6-CONDITION），所以**不伪造"已阻止"**。

## 1. 三级组织里谁负责什么

| 层级 | 是谁 | 负责 | 记忆 |
|---|---|---|---|
| **L1** 管理线 | 管理会话（用户直接对话） | 建线、派任务、批策略、验收、跨线协调 | 长期 |
| **L2** 角色线 | 角色会话（line） | 拆解、**决定自己做还是开 L3**、产出与自检、结果回 L1 | 长期、跨会话 |
| **L3** 线内智能体团队 | 该角色会话里 spawn 的官方 teammate | 并行子任务、交叉验证、一次性质量点 | 短、随任务释放 |
| 文件 | 项目目录 | 记忆与交付证据的唯一事实源 | 持久 |

三个必须知道的边界：
1. 官方任务板的 `ownerName` 只能是 teammate，**L1/L2 不能当任务 owner**（0.6.0 起只读映射，不写回）；
2. L3 是任务型的，**不能当长期角色**——需要跨会话记忆的一律留在 L2；
3. L2 上下文满了走 `line_handoff` / `line_rebind`（换人不换角色，I3/I4），**不要靠开 L3 逃避上下文问题**。

## 2. 判定输入：七个维度（按顺序问）

| # | 维度 | 问题 | 倾向 |
|---|---|---|---|
| D1 | 记忆归属 | 是否需要跨会话/跨重启的长期记忆与历史口径？ | 是 → **L2** |
| D2 | 可拆分性 | 能否切出 ≥2 个互不依赖的子任务？ | 否 → **L2** |
| D3 | 并行收益 | 并行能缩短关键路径（时间窗紧）吗？ | 否 → **L2** |
| D4 | 写盘冲突 | 是否会同时写同一批文件/同一任务板依赖链？ | 是 → **L2 或串行** |
| D5 | 质量点独立性 | 是否需要独立质量点（交叉审查/多方案对比/事实核查）？ | 是 → **L3** |
| D6 | 上下文成本 | 单线一个上下文能否完成？ | 能 → **L2（省钱）** |
| D7 | 风险与回滚 | 失败代价高、必须一次成型？ | 先 L2 出方案，再 L3 并行验证 |

## 3. 决策规则（可直接执行）

**默认：单线自己做（L2）。能 L2 完成就不建队。**

**开 L3 的最小充分条件（任一满足，且不触犯 §3.2 禁令）**

- **A1 并行验证**：≥2 个独立方案/审查视角 → 2–3 名 teammate
- **A2 可切块生产**：≥3 个独立产出单元（文件/章节/模块）→ 2–4 名
- **A3 独立质量点**：审读/校对/事实核查必须在产出后独立执行 → 1 名
- **A4 时间窗**：关键路径长于单线预算，并行能把时间砍半

**始终 L2（不开 L3）**

- B1 需要长期角色记忆与口径（连续性、设定、伏笔、历史决策）
- B2 同写一批文件或同一条任务板依赖链（并行会互相踩）
- B3 任务体量小于一个回合（建队成本 > 收益）
- B4 需要向用户做最终承诺/验收签字
- B5 需要跨会话交接（`line_handoff` 只对线生效，不对 teammate 生效）

**硬约束**：一次建队成员数建议 ≤4（部署级 `maxMembers` 默认 16，不是按线/按任务的限制）；建队必须写 **reason + 预期产出**（进审计）。

**平局裁决顺序**：D5（质量点）→ D2（可拆分）→ D6（成本）；仍不确定时**选 L2**（可回退成本更低）。

## 4. `subteamPolicy` 三档语义（插件已实现，只记录/审计）

| 档位 | 语义 | 谁执行 |
|---|---|---|
| `auto`（默认） | L2 可按本策略自行决定建队 | L2 |
| `ask` | L2 建队前必须先向 L1 请示，L1 用 `line_manager_ack` 批 | L2 问、L1 批 |
| `never` | 禁止建队，任务必须 L2 完成 | L2 |

记录位置：`line_send({ subteamPolicy, maxMembers })` 字段；`line_team_board.lines[]`；`line_department_board` 的 `subteamAudit`。**只记录、不拦截**（0.6.1 设计，守 I5）。

## 5. 一次 L3 委派的标准动作（可直接套用）

1. **拆解**：子任务清单 + 交付物 + 验收点 + **互不重叠的文件写盘范围**
2. **建队**：spawn ×N；每人一段**完整**上下文（teammate 不共享父会话记忆）
3. **并行**：各自写独立文件；**禁止同一文件并发写**
4. **收口**：L2 读全部产出 → 交叉校验 → 合并 → 自检
5. **回 L1**：产出路径 + 关键判断 + 未覆盖项；L3 结束即释放，不留名册
6. **记账**：建队 reason / 成员数 / 实际耗时 / 是否值得（供 §6 复盘）

## 6. 持续更新机制

- 本文带 **版本号 vN + §8 变更记录**，中英同步；随下一个版本发布（文档改动也走发版）。
- **触发更新的信号**（出现任一就改本文，不要等下次重构）：
  1. L3 产出被 L2 驳回率 > 30%
  2. 建队后关键路径没有缩短（无并行收益）
  3. 出现"该自己做却建队 / 该建队却自己做"的事后分歧
  4. 官方 API 变化（per-line 上限、spawn 前拦截、owner=line）
- **更新流程**：改本文 → 中英同步 → 加变更记录 → 随版本发布 → 发版说明引用本条。
- **观察指标**（只观察，不自动拦）：L3 使用率、平均成员数、L2 驳回率、任务平均时长、每任务 token（会话级代理，不伪造任务级）。

## 7. 当前不能自动化的部分（诚实边界）

- 插件**不做**任务识别与自动派发：识别、派发由 L2 的 agent 按本策略执行；
- 官方任务板**不能**把 L1/L2 设为 owner，也不能双向写回（Non-goals T5）；
- **不能**按线/按任务限制成员数（只有部署级 `maxMembers`）；
- 将来官方提供 spawn 前拦截/执行前审批 API，才可把本策略升级为**硬门禁**（对应原 0.6.7 条件）。
