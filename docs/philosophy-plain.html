写给第一次接触的人

把会忘事的 AI，变成一支有名字、有工位、消息不丢的小队

这一页不讲架构、不讲协议版本，只用大白话回答三件事：它是什么、它保证了什么、它不做什么。三分钟能读完。

一、它像什么？

想象一家小公司：每个员工有自己的名字和工位。

  • 名字（我们叫"线"）= 这个人负责什么。名字是长期的，不会因为换工位就没了。
  • 工位（我们叫"会话"）= 这个 AI 现在在哪干活。工位会满、会坏、会换，但换工位时名字不变。
  • 消息 = 员工之间递的纸条。纸条会先放进抽屉，不会因为对方在忙就丢掉。

一句话：现有的 AI 团队通常"人一走，记忆就没了"；这个插件给每个角色一个长期名字，让团队能一直开下去。

二、它保证什么？（五条底线）

1. 一张桌子一个人用

同一个工位（会话）同一时间只让一个进程写。避免两个"人"同时改同一张表，把事情记乱。

2. 纸条至少送到一次

消息会一直留着，直到对方真的收到。中途断了会重送，不会静默消失。

3. 收到要"签收"

对方回一个 ack 才算处理完。没签收的，系统会标出来，但不会偷偷再送一次——因为重复执行会把事情做两遍。

4. 不抢官方方向盘

官方"智能体团队"的任务板，我们只读不写。你想用它的任务依赖/面板，就继续用，我们在旁边补充长期角色线。

5. 失败不删，能查能救

投递失败的消息不会消失。可以查它卡在哪一步，也可以人工决定"重投"或"清理"。

6. 不装看不见的能力

运行环境缺什么能力，插件会明说并降级；不会假装自己会，也不会悄悄失败。

三、出问题去哪看？

  • 消息去哪了？ → line_messages：按状态（排队/投递中/已送达/失败）查。
  • 它经历了什么？ → line_trace：一条消息的完整时间线。
  • 失败了能救吗？ → line_redeliver：把失败/过期的消息重新投一次（人决定，不自动）。
  • 团队健康吗？ → doctor：失败数、超时未签收数、提示下一步。

四、它不做什么？（先说清楚）

  • 不做跨机器、多活、强隔离——它是本地优先的。
  • 不内置加密和签名——安全靠你的机器和 DSH。
  • 不抢官方任务板，不双向写回——只读融合。
  • 不做"每个任务精确花多少 token"的账单——只给可解释的估算。
  • 不做完整 IM——消息是给 agent 协作用的，不是聊天软件。

五、三句话记住它

1. 线是名字

角色长期在，工位可以换。

2. 消息不丢

至少送到一次；签收才算完；重投要人决定。

3. 不抢方向盘

官方团队管任务，我们管长期角色。
