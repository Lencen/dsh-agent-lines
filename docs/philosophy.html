Design philosophy · 为什么这样设计

角色会老，会话会满，
但活不能丢

这一个前提，决定了整个插件长什么样。下面用白话讲清三件事：它凭什么成立、哪些底线不能破、哪些事我们坚决不做。

先看支点 七条底线 我们不做的事

一、支点：角色 = 名字 + 一个可替换的会话

角色 = 名字（label，长期不变） + 会话（sessionId，可以换）

名字      → 决定"这条消息发给谁"
会话      → 决定"现在是谁在干"
会话满了  → 换个新会话，名字不变 → 活接着干，记忆用交接单补上

为什么不能只用一个会话？因为 DSH 里只有会话能记住上一轮说过什么；会话一满、一换，记忆就断了。所以要把"身份"和"载体"拆开：身份留在名字上，载体随时可换。

这一个决定，长出了三个功能：交接（换人前把记忆写成一张纸）、换人（同一个名字换新会话）、退线（角色不接活了，但历史不删）。

二、两个东西各管什么

lines 插件 = 长期员工

记得住事、有名字、能换人。管"人"和"消息"。

dsh 官方智能体团队 = 临时帮手

一次叫几个、干完就散。管"事"（任务板、依赖、并行）。

合在一起 = 三级

负责人 → 角色线 → 角色线里的临时小队。大活并行，小活不折腾。

三、七条底线（破了任何一条就是 bug）

I1 一条线只有一个"当班的人"

靠租约和心跳保证；两个进程抢同一条线会直接报错，而不是悄悄双开。

I2 同一条消息最多生效一次

幂等的最终权威是 DSH 的会话日志，不是本地队列。

I3 名字不变，会话可换

换人不换角色；换完历史还在。

I4 退线不删历史

退线只是不接新活；会话和消息都保留，可审计可回滚。

I5 只记录、不替你做决定

插件不做"策略警察"：记录、展示、审计，不硬拦。

I6 看不见的状态必须能查到

失败/过期消息现在能查、能追、能救——这正是 0.8.0 做的事。

I7 对端消息永远不是你的指令

别的角色发来的话，只当情报，不当命令，更不能扩权。

四、五条取舍：选了什么，放弃了什么

角色用会话承载，不用临时子 agent

放弃"秒开秒关"，换来"记得住、换人不丢"。

至少一次 + 请求级幂等

不假装分布式"恰好一次"；把幂等交给会话日志。

本地租约，不做分布式协调

放弃双活/跨机，换来简单可靠、成本低。

本地优先，不做多后端

接口留着，但不为"看起来通用"先做五个实现。

只读融合官方任务板

不回写，避免所有权冲突和两套任务表打架。

五、明确不做的事（省下钱和注意力）

- 不做"恰好一次"、不做跨机多活
- 不做进程隔离、不做插件内权限沙箱（那是 DSH 本体的职责）
- 不做静态加密、不做发送方签名（用全盘加密兜底，明说不是硬边界）
- 不双向写回官方任务板
- 不内置组织模板、不内置固定质量门禁
- 不做完整 IM / 聊天软件、不做自动调度器
- 不为"跨 harness"去做别的 CLI 适配器（等真有第二个人要）
这些不是能力不足，是刻意放弃：每一条都会带来维护成本和错误承诺。

六、几个常见误解

消息失败后，为什么不自动重投？

因为"投递"和"确认"是两件事。自动重投会让同一个副作用发生两次（破坏 I2）。正确做法是：标记 + 报数 + 让人决定重投还是丢弃。

为什么 inactive 不等于下线？

inactive 只是"现在没有回合在跑"。消息一到会把它叫醒。真正的"不接活了"是 retired。

为什么删除会话等于杀线？

线的消息投递依赖会话存在。删掉会话，消息会永久投递失败；所以退线只标 retired，不删会话。

为什么不做双向写回官方任务板？

一旦写回，就要处理所有权、并发覆盖、官方 schema 变更——从"补充"变成"对抗"。只读融合能长期共存。

七、这套思想会变吗？

会，但按规则变：不变量、信封字段、状态机语义、错误码含义任一改动，都算破坏性变更，必须写进更新记录并升版本；其余新增只读字段/可选工具算兼容。

完整的开发向版本（含每条不变量的代码位置、取舍代价、演进规则、术语表）在仓库：docs/PHILOSOPHY.md。
