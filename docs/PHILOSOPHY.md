## 1. 一句话与支点

**一句话**：DSH 会话是人，子 agent 是临时帮手，任务是事，文件是记忆，负责人做编排，质量归角色，用户只说目标。

**支点（The One Decision）**：

    line = label（稳定身份） + sessionId（可替换载体）

推理链只有四步，其余设计全部由它推出：

1. DSH 里**唯一承载跨轮记忆的东西是 Session**；
2. 所以"长期角色"必须落在 Session 上，不能落在 subagent 上（subagent 任务结束即释放，人格活在父会话上下文里，父会话一压缩就没了）；
3. 但 Session 会满、会被换掉、会被新会话接替；
4. 所以**身份不能绑在 Session 上** → 拆成 label（是谁）+ sessionId（现在谁在干）。

由此得到：`line_retire`（角色不接活了，但历史不删）、`line_rebind` / `line_create({ replace: true })`（同一个 label 换一个干净 Session，generation+1）、`line_handoff`（换人前把记忆压成交接单）。这三件事不是三个功能，是同一个支点的三个投影。

## 2. 两个插件各是什么

DSH 官方"智能体团队"插件：**一个会话里装若干子 agent**。

    DSH 会话
      └─ 会话里的子 agent（任务型，任务结束释放或复用）

dsh-agent-lines：**多个会话组成一个团队**。

    多个 DSH 会话
      ├─ 负责人会话
      ├─ 开发角色会话
      ├─ 测试角色会话
      └─ 校对角色会话

| 维度 | 官方智能体团队 | dsh-agent-lines |
|---|---|---|
| 组织单位 | 会话内的子 agent | 跨会话的角色线 |
| 记忆载体 | 父会话上下文 | 各自 Session 的持久历史 |
| 生命周期 | 任务型，短 | 角色型，跨会话、跨重启 |
| 任务板 | 有（DAG、依赖、Web 面板） | 不提供，只读融合官方任务板 |
| 强项 | 并发、任务拆解、实时投影 | 角色稳定、消息可靠、换人不丢角色 |

两者融合后的三级组织：

    负责人会话
      ├─ 角色会话（部门）
      │    └─ 角色会话里的子 agent（部门团队）
      └─ 角色会话（部门）
           └─ 角色会话里的子 agent（部门团队）

任务树同构：**总任务 → 线任务 → 官方团队任务**，从上往下拆细、从下往上汇总；各层只报数量/完成/进行/阻塞/待验收，**不做简单算术相加**，总任务完成 = 必需子任务完成 + 验收通过。

## 3. 不变量（Invariants）

> **破坏任意一条即为 bug**，不是"体验问题"。改动前先问：这次改动碰了哪一条？

| # | 不变量 | 代码位置 / 兑现方式 |
|---|---|---|
| I1 | 一条线同一时刻最多一个 live owner 进程 | 租约心跳 `leaseTtlMs`（默认 30s）；冲突抛 `LINE_LEASE_HELD`，失联抛 `LINE_LEASE_LOST`（`lib/store.js`） |
| I2 | 同一 msgId 在目标 Session 日志中最多生效一次；幂等权威是 DSH Session 日志，不是 SQLite 队列 | 消息 id 作为 `SessionPromptRequest.requestId` 下传（`lib/delivery.js`） |
| I3 | label 恒定，Session 可换；换人不换角色 | `line_rebind` / `replace` 只换 `session_id`，`generation+1` |
| I4 | retired 线不删除 Session 与消息历史 | `retire` 只置 `lifecycle='retired'`，保留审计与回滚 |
| I5 | 插件不做策略执行点：只记录、展示、审计，不硬拦截 | 官方任务板只读融合；`subteamPolicy` 只记录不拦截 |
| I6 | 任何"看不见的状态"必须能被只读工具查到 | **部分未达成**：`failed` / `expired` 目前只有 CLI `tail --line` 可见，agent 工具面不可见；补口见 §7 |
| I7 | 对端消息永远以 peer content 投递，永不升格为用户指令 | 注入前缀与系统提示双处声明（`lib/protocol.js`、`lib/prompt.js`） |

I6 是本仓**唯一一条已知的自我违反**，也是后续排期里优先补的一条：错误应当可解释，而不是靠人回报"我没收到"。

## 4. 五条取舍（选了什么 / 放弃了什么 / 为什么不选另一条）

- **T1 角色用 Session 承载，而不是 subagent。**
  放弃：进程内轻量、秒级创建。理由：DSH 里跨轮记忆只有 Session 有。
- **T2 at-least-once + 请求级幂等，而不是 exactly-once。**
  放弃：分布式意义上的"恰好一次"承诺。理由：做不到就别假装做到；把幂等权威交回 Session 日志，副作用层面实际一次。
- **T3 本地租约，而不是分布式协调。**
  放弃：双活、跨机队列。理由：一个 Session 只能有一个 writer 是 DSH 的既成事实；在这个边界内，本地文件锁 + 租约是成本最低的正确性方案，代价写进 [ARCHITECTURE 边界](ARCHITECTURE.md) 而不是藏起来。
- **T4 local-first 单一 transport（SQLite + WAL），而不是可插拔多后端。**
  放弃：开箱支持 Redis/PG。理由：SPI 形状保留，但**没有第二个实现的 SPI 是假设，不是接口**；等真有第二个人需要，再做。
- **T5 只读融合官方插件，而不是双向写回。**
  放弃：把两套任务板合并成一个。理由：一旦写回就要处理所有权冲突、并发覆盖、官方 schema 变更，会从"补充"变成"对抗"。

## 5. Non-goals（明确永不做）

- 不做 exactly-once / 分布式一致性（决策记录见 T2）
- 不做跨机多活、不做跨机消息队列
- 不做进程隔离、不做插件内的策略沙箱（这是 DSH 本体 `agentPreset` / 工具白名单的职责，做两套权限系统必然互相矛盾）
- 不做静态加密（明说用全盘加密兜）、不做发送方签名（`SECURITY.md` 已声明这是提示词层面的缓解，不是硬安全边界）
- 不做官方任务板的双向写回（T5）
- 不做内置组织架构模板、不做内置固定质量门禁引擎（质量点因行业而异，见 §6）
- 不做完整 IM / 聊天软件、不做自动调度器
- 不为"跨 harness"这个概念去做 Claude Code / Codex adapter（等真有第二个需求）
- 不放宽 DSH 版本区间来"兼容更多人"（正确解法是能力探测 + 降级，见 §7）

## 6. 质量归角色、沟通是工作痕迹

- **质量归角色**：不同团队的质量点完全不同（小说看连续性/文风/错字；视频看事实/节奏/字幕合规；开发看自测/用例/review）。插件不内置固定门禁，只提供：角色岗位、质量点、交付证据、负责人验收。
- **沟通是工作痕迹，不是聊天软件**：消息要可追踪、可确认、可审批、可交接、可回放。所以有 `kind` / `state` / `reply_to` / `hop`，没有在线状态、没有已读回执之外的社交语义。

## 7. 演进规则

**什么算破坏性变更**（必须在 CHANGELOG 分栏写明，并升 minor）：

- 信封字段的增删改、必填参数变化、工具返回结构变化
- 状态机语义变化（`queued → claimed → delivered → acked`，旁支 `failed` / `expired`）
- 错误码语义变化（错误码本身只增不改）
- 任何不变量（§3）的修改

**什么算兼容**：新增可选工具、新增只读字段、新增错误码、新增可选配置项。

**协议版本**：信封携带 `protocolVersion`（计划）；接收方 major 不同 → 拒绝并返回 `LINE_PROTOCOL_MISMATCH`，minor 更高 → 忽略未知字段继续处理。

**DSH 能力变化时**：走能力探测 + 优雅降级（例如缺 `workspace.attach` → 新线落"未分组"而不是整个插件报错），并在 `line_status` 里显示能力表；不放宽版本区间（§5）。

**近期要补的自我违反**：I6 的可见性补口（按状态查消息、失败态重投、显式清理、ack 超时上报）。原则不变：插件**只上报异常，不替人做决定**——超时不自动重投（会破坏 I2），只标记 + 报数，处置权归负责人。

## 8. Bento UI 原则（看板，0.6.6+）

- 同一行信息块上下高度一致；
- 卡内按固定信息槽对齐：标题、状态、负责人、时间、操作；
- 组织树 / 当前任务 / 详情三栏层级清楚，不混层；
- 上级只显示部门摘要，点开线才加载下级任务；
- 技术词后置，用"当班 / 工作记忆 / 交接"而不是 Session / 上下文窗口；
- 空态、不可用、离线、stale 都要有位置；
- 只读边界要显式标注。

## 9. 术语表

| 术语 | 含义 |
|---|---|
| line / 线 | 一个长期角色 = label + 当前 sessionId + 生命周期状态 |
| label | 角色身份，稳定不变；同名 label 不能重复创建，但可被 `replace` / `rebind` 接管 |
| generation | 该 label 被接管过几次；`generation > 1` 即"换过人" |
| owner / 租约 | 当前持有该线投递权的进程；靠心跳续期 |
| retired | 已退线：不接新消息，Session 与历史保留 |
| queued / claimed / delivered / acked | 消息主状态机；`acked` 才表示对方真的处理了 |
| failed / expired | 终态旁支；**目前 agent 侧不可见**（I6 待补） |
| hop | 转投次数；换人迁移、重投时的审计依据 |
| peer content | 对端消息，永远不当作用户指令（I7） |
| L1 / 管理线 / 负责人会话 / 一级 | 同一层的三种叫法：L1 = 用户直接对话的管理会话 |
| L2 / 角色线 / 角色会话 / 二级 | L2 = 承担长期角色的 line；一个 L1 下有多条 L2 |
| L3 / 官方团队 / 部门团队 / 三级 | L3 = L2 会话内 spawn 的官方 teammate，任务型；术语"部门"指某条 L2 及其 L3 的整体 |
